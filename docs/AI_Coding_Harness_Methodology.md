## 1. 认知基础：为什么需要 Harness

### 1.1 三大结构性痛点

| 痛点 | 没有 Harness 时 | 有 Harness 后 |
|------|----------------|---------------|
| **工序随机** | AI 跳过单测直接部署，构建挂了才发现 | 意图×风险决定流程，同类任务走同一条链 |
| **上下文污染** | 方案设计混入上一段需求的字段名，业务/技术/状态互相串味 | 角色分工、状态外置，各管一段 |
| **坑反复踩** | `mvn -am` 卡死踩过三次，每次换会话都忘 | 坑沉淀成规则，一次踩、永久兜底 |

### 1.2 根因分析

Agent "遗忘"不是 bug，是当前架构的**必然代价**，有三重根因：

| 根因 | 机制 | Harness 对策 |
|------|------|-------------|
| **压缩丢失** | Auto-Compact 省略"看似不重要"的流程步骤 | 规则外置到确定性文件 |
| **检索失败** | 记忆文件存在但没被加载进上下文 | 状态持久化 + 按需加载 |
| **指令遵循失败** | 信息都在但模型仍然跳步 | 门禁阻断（fail-closed） |

### 1.3 核心认知转换

```
旧思维：写更好的 prompt → 说服模型遵守规则
新思维：搭结构性框架 → 不管模型听不听话，越界就被拦住
```

**关键公式**：`prompt = 一次性的说服`，`harness = 结构性的约束`  
模型供给智商，harness 供给纪律。

## 2. Harness 五层架构设计

### 设计总纲：把上下文当预算来管理

> 判断：主会话的上下文是最贵的资源，不是免费的草稿纸。  
> 分层的唯一标准不是"按功能分类"，而是"按何时被读取"——常驻的极小，深的按需加载。

```
┌─────────────────────────────────────────────────────┐
│  Layer 1: 常驻入口层 (≤8K)                           │
│  CLAUDE.md / .cursorrules / project-instructions     │
│  → 角色定义 + 触发规则 + 门禁速查                     │
├─────────────────────────────────────────────────────┤
│  Layer 2: 原子规则层 (7~10 条)                        │
│  rules/*.md                                          │
│  → 每条规则 = 一次事故的墓志铭，单一职责可按需引用      │
├─────────────────────────────────────────────────────┤
│  Layer 3: Agent 调度层                                │
│  agents/ (dispatcher + orchestrator + 执行角色)       │
│  → 流程编排、职责隔离、状态机驱动                      │
├─────────────────────────────────────────────────────┤
│  Layer 4: 按需上下文层                                │
│  context/*.md                                        │
│  → TDD 指南、评审模板、Pre-Mortem 模板等深度内容        │
│  → 只在进入对应阶段时才加载，用完即释放                 │
├─────────────────────────────────────────────────────┤
│  Layer 5: 执行支撑层                                  │
│  skills/ + commands/ + evals/                        │
│  → 工具封装、slash 命令入口、检测脚本                  │
└─────────────────────────────────────────────────────┘
```

### 2.1 Layer 1：常驻入口层

**文件**：`CLAUDE.md` / `CLAUDE.local.md` / `.cursorrules`（按工具适配）

**内容**：
- 角色定义（你是谁、你负责什么）
- 代码偏好（语言风格、命名规范）
- 流程触发规则（什么场景启动什么流程）
- 门禁速查表（G1–G8 或自定义检查点）

**关键设计**：
- 每个项目的配置**自包含**，不依赖全局配置的 `@import`
- 新项目接入只需拷一份模版进去就能独立运作
- **上下文预算：≤ 8K tokens**

### 2.2 Layer 2：原子规则层

**目录**：`rules/`（建议 7~10 条，每条单一职责）

**设计原则**：每条规则都是一次事故的墓志铭

| 规则文件示例 | 约束内容 | 背后事故 |
|-------------|---------|---------|
| `build.md` | 禁用某危险构建参数，只编译单模块 | 全量解析卡死 |
| `branch-hygiene.md` | 提预发前必须先合 master | 多分支集成构建报错 |
| `code-search.md` | 禁用低效搜索方式，强制走专用工具 | 符号搜索误命中、上下文浪费 |
| `test-first.md` | 业务代码改动前必须先有对应测试 | 回归 bug 反复出现 |
| `commit-atomic.md` | 每次提交只做一件事 | 大提交导致回滚困难 |

**复利效应**：坑只踩一次，之后由规则兜底——这是 harness 最朴素也最值钱的复利。

### 2.3 Layer 3：Agent 调度层

详见 [第 5 节](#5-agent-拆分原则薄主会话--职责隔离)。

### 2.4 Layer 4：按需上下文层

**目录**：`context/`（建议 8~12 个文件）

**典型文件**：
- `tdd-guide.md` — TDD/ATDD 开发指南
- `pre-mortem-template.md` — 事前验尸模板（假设项目失败，倒推原因）
- `adversarial-debate.md` — 对抗辩论规范（业务 vs 技术 vs 质量三方 PK）
- `evidence-chain-spec.md` — 证据链规范（改动必须有可追溯的证据）
- `code-review-checklist.md` — 代码审查清单
- `adr-template.md` — 架构决策记录模板

**科学依据**：
- LLM 注意力呈 **U 型分布**，中部信息准确率显著下降（Stanford "Lost in the Middle", TACL 2024）
- 声称支持 32K+ 的模型仅半数能在该长度保持可靠性能（NVIDIA RULER）

**设计原则**：上下文不是越大越好的"免费缓冲区"，而是需要精心管理的稀缺资源。

### 2.5 Layer 5：执行支撑层

**三个子目录**：

| 子目录 | 作用 | 示例 |
|--------|------|------|
| `skills/` | 封装工具链为 AI 可调用的能力 | 日志查询、构建脚本、部署命令 |
| `commands/` | slash 命令入口 | `/init-harness`、`/learn`、`/audit` |
| `evals/` | 检测脚本 | 编译检查、单测覆盖率、规则合规性 |

**经验三级进化机制**（`auto-learn` 规则驱动）：

```
第一次踩坑 → lesson（单次记录）
    ↓ 第二次在不同场景又遇到
归纳为 pattern（条件模式："Mac + 某依赖 = 禁用某参数"）
    ↓ 第三次验证后
晋升 instinct → 自动注入所有新项目的规则
    ↓ 每一级晋升都需要人工确认
防止错误经验扩散
```

## 3. 稳定性的两大支柱：门禁 + Hook

### 3.1 为什么验证比执行更重要

> **研究发现**（arxiv 2605.29682）：原始 token 消耗和工具调用仅解释 agent 成功率方差的 R²=0.33~0.42，而**验证反馈质量**（Effective Feedback Compute）达到 R²=0.94~0.99。

**结论**：决定 AI 干活靠不靠谱的不是"给它多少预算"，而是"检查做得多好"。

### 3.2 G1–G8 门禁墙（硬校验）

每个门禁是**确定性的函数/脚本**，检查产物存不存在、编译过不过、单测通没通。

| 门禁 | 检查点 | 失败行为 |
|------|--------|---------|
| G1 | 需求文档完整性 | 退回需求评审 |
| G2 | 方案设计文档 + ADR | 退回方案设计 |
| G3 | 编译通过 | 退回开发 |
| G4 | 单元测试通过 | 退回开发 |
| G5 | 代码审查通过 | 退回修改 |
| G6 | 预发部署成功 | 退回部署 |
| G7 | 接口测试通过 | 退回测试 |
| G8 | 验收报告 | 人工确认（暂不自动化） |

**核心原则**：任一 gate FAIL 则流程**退回**对应阶段——不是"建议"，是"阻断"。

### 3.3 Hook 拦截（运行时围栏）

Hook 在工具调用**执行前**拦截，做两件事：

1. **状态文件写操作**只允许编排层 Agent 触发（其他 Agent 绕过直接 reject）
2. **危险操作**（`git push --force`、`rm -rf`、删除数据库等）弹确认

**Hook 不是事后审计，是实时围栏。**

### 3.4 总原则

> 流程强制执行必须从 LLM 推理**中外置**到确定性基础设施。  
> 不能依赖模型"记住"该执行哪个步骤——门禁必须是确定性代码，独立于上下文窗口，**fail-closed**（默认拒绝，只放行显式允许的操作）。

## 4. 动态流程编排：意图 × 风险裁剪

### 4.1 不是每个任务都走全流程

完整流程链路（以研发场景为例，共 19 个节点）：

```
需求评审 → 需求确认 → 方案设计 → 方案确认 → Pre-Mortem → 实施计划 → 验收标准确认
→ 拉变更 → 建分支 → 建 worktree → 开发 → 编译 → 单测 → ATDD → 证据链
→ 部署预发 → 接口测试 → 上线确认 → 验收报告
```

**但绝不是每个任务都走全 19 步！** 由**意图 × 风险**动态裁剪：

| 意图 × 风险 | 实际走的节点 |
|-------------|-------------|
| QUERY / 纯查询 | **0 个必需**——识别对了就根本不该启动流程 |
| BUG_FIX · LOW | **快速路径**：开发 → 编译 → 单测 → 证据 → 报告 |
| FEATURE · MEDIUM | 再加上方案设计、对抗辩论、TDD |
| FEATURE · HIGH | **19 节点拉满** + ADR 架构决策记录 |

### 4.2 硬规则：改完必部署

> 只要检测到真实业务代码改动，自动把**部署预发 + 接口测试**追加为必需节点。  
> 堵死"改了代码、没验证就收工"的漏洞。

### 4.3 泛化到你的项目

你可以根据项目类型定义自己的节点和裁剪规则：

**Web 前端项目**：
```
LIGHT:  开发 → lint → 单测 → 截图对比 → 报告
MEDIUM: 设计评审 → 开发 → lint → 单测 → E2E → 截图对比 → 报告
HEAVY:  需求评审 → 设计评审 → 开发 → lint → 单测 → E2E → 性能测试 → 部署 → 验收
```

**数据工程项目**：
```
LIGHT:  SQL 编写 → 语法检查 → 数据验证 → 报告
MEDIUM: 方案设计 → SQL 编写 → 语法检查 → 数据验证 → 影响评估 → 报告
HEAVY:  需求评审 → 方案设计 → SQL 编写 → 语法检查 → 数据验证 → 影响评估 → 预发布 → 回归 → 报告
```

## 5. Agent 拆分原则：薄主会话 + 职责隔离

### 5.1 核心设计思想

> 主会话应该退化成一个"什么都不想、只执行 dispatcher 指令"的纯执行器。  
> 这反直觉——我们本能地想让主模型更全能；但全能恰恰是污染之源。

**类比**：像微服务里的 thin controller，不是它不行，是它不该管。

### 5.2 Agent 分类（四类）

| 类别 | 角色 | 为什么不能合并 |
|------|------|---------------|
| **调度 + 合成** | dispatcher（路由）+ orchestrator（合成） | dispatcher 只读状态做路由，orchestrator 只读观点做合成——职责正交，合并会导致"裁判兼选手" |
| **多角色评审** | 角色A（业务）/ 角色B（技术）/ 角色C（质量） | 必须独立思考、互不看到对方初稿，才有对抗性；合成后反而更省 token |
| **流程执行** | planner → developer → verifier → deployer → tester | 每个节点的 system prompt 和可用工具完全不同——合并意味着同时暴露所有工具，等于没约束 |
| **意图分类** | intent-classifier | 单独分类避免执行 Agent 既当裁判又当选手 |

### 5.3 三条铁律

1. **主会话只听 dispatcher**：dispatcher 读状态文件返回"下一步调谁"，主会话照做，禁止自己越权读取其他 Agent 的产出
2. **职责隔离**：每个 agent 的可用工具严格受限（如 developer 有 Edit/Bash，verifier 只有 Read/Bash）
3. **上下文 ≤ 阈值**：主会话只加载入口规则 + 触发规则 + 最近一条 dispatcher 指令

### 5.4 交接方式选择

| 方式 | 适用场景 | 代价 |
|------|---------|------|
| **文件交接**（推荐起步） | 控制平面、状态持久化 | 文件管理成本 |
| 消息驱动（Agent Team） | 计算平面、高并行任务 | 状态丢失风险 |
| 脚本编排（Workflow） | 确定性控制流 | 灵活性差 |

**建议**：从文件交接起步，状态外置到 JSON/YAML 文件，通过 dispatcher 状态机驱动。当项目规模增大后再考虑混合方案。

### 5.5 代价坦白

| 得到 | 付出 |
|------|------|
| 职责隔离，杜绝上下文污染与越权 | 链路变长，一次需求要在多个 agent 间转交 |
| 状态外置，可中断可续跑 | 调试更难，一个 bug 要跨 agent 追 |
| 单 agent 上下文可控 | agent 间通信本身有 token 与协调开销 |

## 6. 四阶段演进路径（避坑地图）

> 这不是设计出来的，是被现实一路逼出来的。

### 阶段 1：拿来主义

- **起点**：使用社区开源模板（如 oh-my-claudecode、everything-claude-code 等）
- **收获**：从"裸用 AI"跨进"有章法地用 AI"
- **天花板**：通用规范覆盖不了你的具体开发流程
- **触发词**：当你要写的额外 prompt 比规范本身还长时 → 进入阶段 2

### 阶段 2：重 Prompt 约束

- **做法**：把所有流程规矩写进一个大配置文件
- **三天后崩了**：
  - 不听话——规则太多，模型开始"选择性遵守"
  - 上下文爆炸——所有规则常驻窗口，留给代码的空间被挤压
  - 自我矛盾——规则间偶尔冲突，模型编造折中方案
- **核心教训**：prompt 约束是说服，不是强制。你无法用更多的字来对抗概率性的遗忘。

### 阶段 3：减负 + 分层加载

- **做法**：
  - 常驻 prompt 砍到只留角色定义 + 触发规则（≤8K）
  - 深度内容移到按需加载层
- **效果**：立竿见影，模型终于有"脑容量"去理解代码了
- **新问题**：长程会话中，规则被代码输出稀释到注意力衰减区，模型又开始忘

### 阶段 4：Agent 调度编排

- **做法**：不再约束模型"你该怎么做"，而是让不同的 agent 各司其职、互相制衡
- **效果**：状态外置、决策收敛给 dispatcher，即使单次会话崩了，状态不丢、流程能续
- **陷阱**：过度拆分（24 个 agent）导致协调成本过高 → 需要精简到核心必要角色

**关键认知**：真正需要警惕的不是"agent 多"，而是"agent 间耦合多"。输入输出是清晰的文件/JSON、不需要会话协商，数量就不是问题。

## 7. 可落地的 Checklist

### 第一天：最小可用 Harness

- [ ] 创建项目级 `CLAUDE.md`（或对应工具的配置文件），控制在 **≤ 8K tokens**
- [ ] 写入 3 条最痛的规则（从你最近踩的坑中提炼）
- [ ] 定义你的项目类型对应的 3 级流程裁剪规则（轻/中/重）
- [ ] 设置一个"改完必部署"硬规则

### 第一周：规则沉淀

- [ ] 建立 `rules/` 目录，每踩一个坑就沉淀一条规则
- [ ] 每条规则包含：约束内容 + 背后事故 + 触发条件
- [ ] 建立 `context/` 目录，把深度指南从常驻配置中移出
- [ ] 配置 hook 拦截危险操作（`git push --force`、`rm -rf` 等）

### 第二周：门禁体系

- [ ] 定义你的 G1–G_n 门禁（建议从 G1 编译通过 + G2 单测通过 开始）
- [ ] 每个门禁是确定性脚本，不是"建议"而是"阻断"
- [ ] 门禁失败自动退回对应阶段

### 第一个月：Agent 编排

- [ ] 从"薄主会话"开始：主会话只做调度和执行
- [ ] 拆出 dispatcher（路由）+ 至少一个专职 Agent
- [ ] 状态外置到 JSON 文件，支持中断后续跑
- [ ] 建立 `/learn` 命令，把踩坑经验自动沉淀

### 持续优化

- [ ] 经验三级进化：lesson → pattern → instinct
- [ ] 定期审计：规则是否过时？门禁是否遗漏？Agent 职责是否清晰？
- [ ] 记录每个规则背后的事故，防止"不知道为什么有这条规则"就删掉

## 8. 我的项目适配模板

### 8.1 目录结构模板

```
my-project/
├── CLAUDE.md                    # Layer 1: 常驻入口（≤8K）
├── CLAUDE.local.md              # Layer 1: 项目本地配置（自包含）
├── rules/                       # Layer 2: 原子规则
│   ├── build.md                 # 构建规范（禁用危险参数等）
│   ├── test-first.md            # 测试先行规范
│   ├── commit-atomic.md         # 原子提交规范
│   ├── branch-hygiene.md        # 分支管理规范
│   ├── code-search.md           # 代码搜索规范
```

### 8.2 CLAUDE.md 模板（常驻入口层）

```markdown
# 项目角色

你是这个项目的 AI 开发助手，遵循以下规范。

# 代码偏好
- 语言：[你的语言]
- 风格：[你的风格偏好]
- 测试框架：[你的测试框架]

# 流程触发规则
- 纯查询（QUERY）：直接回答，不启动流程
- Bug 修复（BUG_FIX）：走快速路径 → 编码 → 编译 → 测试 → 报告
- 功能开发（FEATURE）：走完整流程 → 需求 → 设计 → 编码 → 编译 → 测试 → 部署 → 验收
- 重构（REFACTOR）：走中等路径 → 设计 → 编码 → 编译 → 测试 → 报告

# 硬规则
- 改完必部署：检测到业务代码改动，必须部署并验证
- 禁止危险操作：git push --force、rm -rf 等需人工确认
- 提交前必须通过所有门禁

# 门禁速查
- G1: 编译通过 → 失败退回开发
- G2: 单测通过 → 失败退回开发
- G3: 代码格式检查 → 失败退回修改
```

## 附录：核心原则速查

| # | 原则 | 一句话 |
|---|------|--------|
| 1 | **上下文是预算** | 不是越大越好，按"何时被读取"分层管理 |
| 2 | **规则是墓志铭** | 每条规则背后都是一次真实事故 |
| 3 | **门禁是阻断** | 不是"建议"，是"越界即退回"的硬墙 |
| 4 | **hook 是围栏** | 实时拦截，不是事后审计 |
| 5 | **主会话是薄 controller** | 只听 dispatcher，不思考业务细节 |
| 6 | **职责必须隔离** | 裁判≠选手，routing ≠ synthesis ≠ execution |
| 7 | **状态必须外置** | JSON/YAML 文件，可中断可续跑 |
| 8 | **验证 > 执行** | R²=0.94~0.99 vs R²=0.33~0.42 |
| 9 | **fail-closed** | 默认拒绝，只放行显式允许的操作 |
| 10 | **经验要进化** | lesson → pattern → instinct，人工确认每一步 |

---

> **最后的话**：Harness 不是一次性设计出来的，而是被现实一路逼出来的。从最小可用开始（第一天 checklist），每踩一个坑就加固一层，让框架和你一起成长。记住：模型供给智商，harness 供给纪律。
